# TailView

TailView is a private, experimental Mac screen and audio bridge for up to two paired iPhones or iPads at once. The Mac app opens a window and also stays available in the menu bar when that window is closed. An already paired device connects when its iOS app opens, shows the main Mac display, and can use the Mac mouse and keyboard. One connected device at a time plays Mac app and media sound and sends its microphone to BlackHole 2ch. TailView sends data directly over the existing Tailscale connection; it has no account service or Jump Desktop dependency.

## Build and install

Run `xcodegen generate`, then build the **TailViewMac** and **TailViewIOS** schemes in Xcode. The project currently uses Alex's Apple development team and separate Mac/iOS bundle identifiers. Both devices must be signed in to Tailscale. The Mac needs Screen Recording and Accessibility permission, and iOS needs Microphone permission. Mac app and media sound is captured with ScreenCaptureKit; it does not need BlackHole. To use the incoming iPad or iPhone voice in a Mac app, install [BlackHole 2ch](https://github.com/ExistentialAudio/BlackHole). While a paired viewer is connected, TailView automatically enforces **BlackHole 2ch** as the Mac's default input and locks playback and system sound to the physical speakers or headphones selected at connection time. If that output disappears, it falls back to another physical output, preferring built-in speakers. It corrects changed defaults while connected and restores the previous selections when the last paired viewer disconnects, access is paused, or TailView quits. A saved device that has disappeared falls back to built-in hardware. A recovery journal restores TailView-owned selections on the next launch after a crash without overwriting later user selections. The Mac window shows the enforced routes or a routing failure. Apps with their own explicitly selected input still need **BlackHole 2ch** chosen in their settings; apps using the system default follow automatically. BlackHole is never chosen as the session's Mac playback output because that would loop Mac sound into the remote microphone input.

## First connection

1. Open TailView Mac from Applications or the Dock. Its window shows the current access state. It starts sharing automatically unless access was previously paused; choose **Resume Access** if needed. The app stays in the menu bar while running, and **Open TailView** in that menu brings its window back. To keep TailView out of the Dock, turn off **Show in Dock** in the window's **App** section or in the menu bar menu; TailView then runs only from the menu bar.
2. Choose **Pair a new device** in the window or **Pair a New Device** in the menu bar. The window shows the Mac's Tailscale address and a temporary pairing code. Pairing closes after five minutes or after a successful pairing.
3. Open TailView on the iPhone or iPad, enter that address and code, and tap **Pair and connect**. This saves a random credential in the iOS Keychain. The Mac stores a digest in its Keychain.
4. Grant the initial system permissions. If macOS asks you to restart TailView after granting Screen Recording or Accessibility permission, relaunch it.

On later launches, each saved device connects without a code or a Mac approval click. A second device can pair while the first is connected. The iOS app retries while it is foregrounded if the Mac host is temporarily unavailable. If a saved credential is rejected, pair again. From iOS 0.4.24, **Reconnect** and automatic connection use the saved Mac this device last signed in to, so pairing again replaces an older saved profile, and a profile the Mac rejects is skipped for the newest other saved profile for the same Mac address, never a different Mac. Earlier versions kept the first saved profile as the default, so an iPad paired more than once could keep offering a revoked credential and fail to reconnect. From iOS 0.4.25 and Mac 0.5.10, a device that iOS starts before it is first unlocked waits for the unlock and then loads its saved Macs, instead of showing the pairing screen as if it had none, and the Mac answers that a device was revoked only when it could read its paired-device list; if it could not, the device keeps its profile and retries. The Mac window and menu bar item have **Pause Access**, which disconnects both viewers and stops screen capture, microphone return, and remote input. Pause remains in effect after relaunch until **Resume Access** is chosen. The Mac window can revoke a paired device.

## Display privacy (formerly Display Control)

TailView Mac includes the features of the former Display Control app, in its window's **Display privacy** section and its menu bar item. Quit the standalone Display Control app after installing this version, since both apps would control the same backlight and input.

- **Blackout Display (Backlight Off)** sets the built-in display backlight to zero, remembers the previous brightness, and holds zero against brightness keys and automatic-brightness changes. TailView keeps sharing the screen while it is dark. Choose **Restore Display Backlight** to restore the saved brightness.
- **Advanced → Disconnect Built-In Display…** disconnects the physical display only when another display, such as an external monitor or a virtual display, is active. TailView moves screen sharing to the remaining main display without disconnecting viewers. The built-in display reconnects automatically after 15 seconds unless **Keep Disconnected** is chosen, and immediately if no other display remains. **Reconnect Built-In Display** restores it.
- **Block Local Keyboard & Mouse When Blacked Out** is a saved setting. When it is on, starting a blackout first verifies that the input shield can start, then filters physical keyboard, system keys (including brightness), mouse, and trackpad events. TailView's own remote control and other software-posted input still work. Restoring the backlight releases local input without clearing the setting. There is intentionally no physical-keyboard escape. If macOS disables the shield while a blackout is active, TailView keeps the backlight off, disconnects the built-in display when another display makes that safe, and requests the macOS lock screen.
- **Launch at Login** registers TailView Mac with `SMAppService`. Unlike Display Control, it is off by default, because a launched TailView also resumes access for paired devices unless access was paused.

Quitting TailView normally restores the backlight and reconnects the built-in display. A saved marker makes the next launch restore them after a crash. Restarting the Mac is the emergency fallback. The backlight and disconnect features use undocumented Apple interfaces and may need updates after a macOS release. The input shield uses the Accessibility permission TailView already needs for remote control. Multi-finger macOS gestures such as switching Spaces may remain available, since macOS handles them outside the keyboard and pointer event stream. The shield protects an active remote session; it does not replace the macOS lock screen or FileVault.

## iPad and iPhone controls

The floating bar's **Mic** button mutes voice sent to the Mac, and its **Speaker** button mutes Mac sound played on this device. They affect the current session independently, and automatic reconnection preserves those choices. The automatic audio settings apply when starting a new session. Muting one direction leaves the other available. An orange **Mic** icon with an x means the microphone is unmuted but nothing is being sent: another device owns audio, or capture is waiting, failed, or restarting. Muting and unmuting retries immediately.

The connected screen uses a compact control bar above the keyboard. Text and Backspace go straight to the focused Mac app without a local message field or Send button. Backspace, including its auto-repeat while held, works from both the iOS keyboard and a hardware keyboard; iOS 0.4.21 and earlier dropped it because the hidden input field is always empty. Tap **Keyboard** to show or hide the iOS keyboard. The bar has **Function (fn)**, **Control (⌃)**, **Option (⌥)**, and **Command (⌘)** buttons. Because a Mac keyboard applies its Fn layer in hardware, TailView Mac 0.5.6 and later translate it: Fn with Delete is forward delete, Fn with the arrow keys is Home, End, Page Up, and Page Down, and Fn with 1–0, -, and = sends F1–F12. Fn with a letter is sent with the Fn flag for Globe shortcuts. Press and hold **fn** (it turns green) to hold the Mac's Fn key itself until you lift your finger, for hold-to-talk dictation; this needs TailView Mac 0.5.7. The Mac releases it if that device disconnects, control ends, or the app leaves the foreground. A tool that reads the physical keyboard directly instead of macOS key events will not see it. Update the Mac before the iPhone or iPad, since an older Mac host disconnects a viewer that sends Fn. Tap a modifier once to apply it to the next key, click, drag, or scroll event. Tap it twice quickly to keep it active for several actions; tap it again to release it. Blue means next action, orange with a lock means held. Modifier state clears when control ends or the app leaves the foreground. A pasted or composed multi-character string is sent as ordinary text even if a modifier is selected. Tap the Mac screen to click, two-finger tap to right-click, slide one finger to move the pointer, press and hold then move to drag, swipe two fingers to scroll the Mac, and pinch to zoom. While zoomed, **Pan view** in the bar temporarily makes two-finger movement pan the screen instead of scrolling the Mac. Settings can reverse the two-finger scroll direction on both axes without changing Pan view or the labeled scroll buttons. The bar also has **Previous Space**, **Next Space**, **Mission Control**, and **App windows** buttons, which send macOS's default Control-arrow shortcuts regardless of the modifier buttons. **Left half**, **Right half**, and **Fill screen** move the Mac's frontmost window to that part of its screen, leaving the menu bar and Dock uncovered. TailView Mac does this through the Accessibility permission it already uses for control, so it works without keyboard shortcuts; an app can still refuse sizes smaller than its minimum. The bar also holds click, drag, scroll, Return, Tab, Delete, Escape, and arrow-key buttons, plus Pan view and zoom reset while zoomed. When it is wider than the screen, swipe the bar sideways to reach the rest. One connected device owns both Mac sound playback and microphone input. A paired iPad has priority until another paired device chooses **Settings → Audio device → Use audio on this device**. The other device retains screen and control access without activating its audio session. Audio passes to the remaining viewer if its owner disconnects, and an explicit choice returns when that device reconnects during the same Mac sharing session. Both paired devices can control the Mac while connected. Playback follows the selected output, including AirPods, on the audio-owning iPhone or iPad; Settings shows the active output. iOS Settings can turn either audio direction off and can align the screen to the top. The audio owner is configured to keep its connection while TailView is in the background; a viewer with no active audio may be suspended by iOS and reconnects on return.

The iOS software keyboard may be hidden when a hardware keyboard is attached or simulated. In one physical iPad Device Hub session, UIKit reported a focused text field and only a 68-point keyboard accessory strip. Type on the hardware keyboard in that case; the **Keyboard** button then turns remote typing off and on. Device Hub keyboard settings can affect whether the native software keyboard appears. Device Hub itself cannot show a physical iPad's screen while TailView has its microphone active. For screen and keyboard testing, open Device Hub before starting TailView. For microphone testing, quit Device Hub entirely and relaunch TailView on the iPad so capture starts with the physical microphone available. One launch immediately after closing Device Hub still measured silence; subsequent normal launches delivered audio after the screen session finished tearing down.

## Lock screen controls

From iOS 0.4.23, a connected paired iPhone or iPad shows a Live Activity on the lock screen and, on iPhones that have one, in the Dynamic Island. It names the Mac, shows Connected or Reconnecting, and has **Mic**, **Sound**, **fn** and **Return** buttons that work without unlocking. From iOS 0.4.30 the buttons are icons, since four named buttons don't fit (VoiceOver still reads their names), and **Return** presses the Mac's Return key, for example to send dictated text. Return is greyed out while Fn is latched, so the Mac never gets fn-Return and a dictation tool can paste before Return submits. Lock-screen buttons can only be tapped, so fn latches: **fn** holds the Mac's Fn key, for example for hold-to-talk dictation, and a second tap (green while held) lets go. Locking the phone or leaving TailView releases a press on the bar's fn button but not a latched Fn; while latched, the bar's fn button is green and tapping it releases Fn. The Mac still releases Fn if the device disconnects or control ends. Muting from the lock screen while TailView is in the background keeps audio running silently: the microphone keeps capturing but sends nothing, and Mac sound plays at zero volume. iOS can refuse to start the microphone from the background, and stopping all audio would let it suspend TailView. These become ordinary mutes when TailView returns to the foreground. iOS starts a Live Activity only while the app is in the foreground, so the controls appear once TailView connects on screen; they end on Disconnect. **Settings → Lock screen → Show lock screen controls** turns them off.

## Audio and connection recovery

TailView Mac 0.5.9 and iOS 0.4.22 compress audio with AAC-LC at 48 kHz: about 64 kbps for the microphone and 128 kbps for stereo Mac sound, instead of 768 and 1,536 kbps of raw PCM. After signing in, each side sends a capabilities packet, and AAC is used only when both offer it; older viewers keep PCM. A viewer sends a capabilities packet older hosts do not understand, so update the Mac first.

Video is tuned for low latency, audio for clean playback; they are not synchronized. The host captures up to 15 frames per second. A current viewer acknowledges each screen frame, and the host keeps at most two unacknowledged frames in flight, always sending the newest frame next instead of queueing old ones in the TCP send buffer. The frame rate therefore follows the link, and the screen is at most about one round trip plus two frame transfers behind. The viewer stops acknowledging while TailView is not active, which pauses video and leaves a locked phone's connection to audio; it resumes with the latest frame on return. Older viewers keep the former unacknowledged sending, capped at 8 frames per second. The Mac window's **Viewer link** row reports frames per second, video and sound throughput, and the average and maximum frame round trip every 10 seconds; the same line is logged under the `com.10x.tailview.mac` subsystem.

A watchdog rebuilds the iPhone audio graph if the microphone tap stops delivering audio for two seconds while the engine claims to run, or delivers only digital silence for four seconds (at most once every 30 seconds). Neither case raises an iOS notification. In the foreground, audio rebuilds keep retrying at up to five-second intervals; in the background they stop after five attempts until TailView returns. An interruption that ends without iOS's resume hint resumes immediately when TailView is in the foreground. Launching the iOS app with `--tailview-health` prints a health line every 10 seconds: connection, microphone, playback queue, sent and dropped microphone frames, screen frame rate, and Mac sound level.

Both directions now buffer roughly 600 ms before playback. The Mac microphone sink uses a fixed-capacity ring buffer, waits to refill after an underrun, and fades the edges of a gap. It caps retained microphone audio at three seconds and catches up to a fresh 600 ms window after an overflow. Clearing a session or changing the audio owner clears that buffer. This deliberately adds voice latency to absorb short delivery stalls; it cannot hide an outage longer than the available audio.

The iPhone bounds pending microphone sends by two seconds of audio instead of eight hardware-dependent tap buffers. Each capture has its own generation, so completions from a stopped capture cannot release the current capture's capacity. Mac sound sends also have a two-second duration budget, expire after two seconds in the application queue, and suppress new screen frames while audio is backed up. iPhone playback retains the existing three-second cap, and short notification sounds start after a 600 ms maximum pre-roll wait even if no more samples arrive.

Both endpoints enable TCP keepalives (10 seconds idle, three probes three seconds apart). The viewer also bounds TCP retransmission time at 20 seconds and retries saved connections after 1, 2, 4, then at most 8 seconds between attempts. Retries live in the connection model, so active audio can recover while the phone is locked. A running, user-enabled microphone continues across a transport outage, discarding samples until the new connection authenticates and receives audio ownership. A connection/capture generation gate prevents old callbacks from changing the new send budget. Explicit disconnect, cancellation, or credential rejection stops capture and retries. Playback-only sessions request limited iOS background time; indefinite background recovery requires an active audio session, and a viewer with both directions muted may need to return to the foreground.

Only an explicit `NO` reply from the updated Mac marks a saved credential as rejected; a truncated or dropped sign-in remains retryable. Connection callbacks verify their connection identity before tearing down state, and Mac sockets are closed only after their reader and queued writers finish. Old clients remain compatible; an old host cannot explicitly distinguish revoked credentials from a dropped sign-in for the new client.

From iOS 0.4.27, TailView's audio sessions are mixable, so another app's sound plays alongside Mac sound instead of pausing it (Mac sound also plays over music). On 2026-10-08, Claude dictation on the locked iPhone interrupted TailView's audio; iOS suspended TailView five seconds later and the Mac connection dropped. When the interruption ended, the old app turned audio off while reconnecting, and iOS suspended it again. TailView now keeps audio running through a connection loss. It also keeps silent playback running whenever audio is wanted but the microphone or Mac sound cannot start, and it rebuilds audio on reconnect if the engine stopped during the outage. While the Mac stays unreachable this keeps retrying indefinitely, which costs battery. Lock-screen updates expire after 90 seconds unless the running app confirms them every 30 seconds, so a suspended or ended TailView shows **Not running – open TailView** instead of a stale Connected.

From iOS 0.4.29, TailView records connection, interruption, route and microphone events, including iOS error codes, in the unified log (subsystem `com.10x.tailview.ios`) and in `Library/Caches/TailView.log` (trimmed at 1 MB). Copy that file from a connected development build with `xcrun devicectl device copy from --device <id> --domain-type appDataContainer --domain-identifier com.10x.tailview.ios.dev --source Library/Caches/TailView.log --destination TailView.log`. That log showed that after dictation on a locked iPhone, iOS lets the microphone restart only in the moment the interruption ends; every later background attempt failed with `'!int'`. In the background TailView therefore reuses a running audio session instead of re-activating it, so the resumed microphone stays on. It still stops after five background attempts. If the microphone stays off, opening TailView restarts it.

Audio route changes rebuild the iPhone's audio graph with up to five delayed retries, preserving the user's requested microphone/playback state. Interruptions clear queued audio; playback resumes automatically when iOS permits it, or through a foreground/user action. Media-services resets rebuild the graph as well. Built-in iPhone playback defaults to the loudspeaker when the microphone is running. The route option follows [Apple's category-routing guidance](https://developer.apple.com/library/archive/qa/qa1754/_index.html); external headphone routes still need device-specific listening checks.

## Verification and limits

On 2026-10-02, the audio reliability tests exercised 20 seconds of 400 ms delivery bursts, startup/refill thresholds, gap fades, overflow catch-up, session clearing, stale send completions, and fragmented/transient authentication replies. The transport suite also verified survival of a 700 ms blocked receiver, release after a longer blocked send, and eight replacements with queued screen/audio writes. All existing viewport, modifier, display-control, and audio-routing smoke suites passed.

Mac 0.5.5 build 23 and iPhone 0.4.15 build 39 were built and signed; the phone install was verified over CoreDevice `localNetwork`. On the physical iPhone, a forced audio-engine stop recovered on the first attempt and resumed non-silent microphone input. With the initial build 38, independent BlackHole captures measured mean/peak -55.3/-34.3 dBFS before a host restart and -57.9/-35.8 dBFS after automatic reconnection. The final build 39 confirmed the built-in Speaker route with microphone capture active, and its playback completion callback confirmed non-silent Mac sound after a short test sound. These are transport/audio-engine checks, not a subjective listening result. Actual calls, Bluetooth changes, extended Wi-Fi outages, and cellular behavior remain separate acceptance checks.

The follow-up iPhone 0.4.16 build 40 was installed over verified CoreDevice USB and read back as the exact version/build. In Alex's cellular configuration, the app stayed connected for several minutes and an eight-second BlackHole check measured mean/peak -56.9/-40.3 dBFS. A Mac-host stop followed by relaunch 41 seconds later caused retries through the 1/2/4/8-second backoff; the app then authenticated automatically and both sent-microphone and received-Mac-audio counters resumed. A subsequent BlackHole check measured mean/peak -61.6/-31.0 dBFS. Playback buffering refilled several times during the run, including the deliberate outage; this is recovery evidence, not proof of gap-free listening. That host-restart check ran with the phone foregrounded. Both target builds and all six smoke suites passed, including reauthorizing an ongoing microphone tap, dropping outage samples, ignoring old connection/capture completions, and resetting the retry delay.

With the same build 40, CoreDevice reported `passcodeRequired: true` while the app logged `background=true`, ongoing audio traffic, and non-silent Mac playback. This is still a prototype. It captures only the main display as JPEG at up to 15 frames per second and 1280 pixels wide when Mac sound is inactive (1024 pixels and lower quality while it is active). Video is JPEG rather than H.264 or HEVC, so it needs several times the bandwidth of a video codec. Mac sound and the microphone share the connection with video; clipboard, files, and multiple monitors are not yet implemented. Sustained network bandwidth below the audio rate can still cause gaps. It has not undergone a full security review. It binds TCP port 47820 to the Mac's Tailscale IPv4 address, accepts up to two simultaneous viewers, and relies on Tailscale encryption. Two viewers share the same Mac mouse and keyboard, so their actions can interfere if both control it at once. A saved Keychain credential can initiate a screen, sound, and control session whenever Mac access is on, so revoke lost devices and use **Pause Access** when access is not wanted.
